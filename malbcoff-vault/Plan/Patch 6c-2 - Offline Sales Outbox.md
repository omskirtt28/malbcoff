# Patch 6c-2 — Offline sales outbox (POS checkout)
**Status: DONE 2026-10-17.** If the internet drops at **Confirm**, the sale is saved on the cashier's device and sent automatically when the connection is back. A sale is never lost and never recorded twice. Builds on [[Patch 6a - Weak Internet Safe Retry]] (the sale's idempotency key = its **client id**), [[Patch 6b - Offline Shell and Cache]] (banner), [[Patch 6c-1 - Offline Outbox for Stock Actions]] (outbox, sender, lock, backoff, Outbox panel, Queued badge, owner Needs Action) and [[Patch 8 - Price at Checkout]] (the typed prices are part of the payload). Feature note: [[POS]]. Schema: [[Migrations]] `P3_005`.

## What the cashier sees
1. Checkout → Set Prices → Confirm Sale → (cash check) → "Complete this transaction?" works as before.
2. **Confirm** and the request fails because of the network, a 5xx, or an expired login → the sale goes into the outbox (same card flow as 6c-1, but no card): a compact state in the confirm dialog — **"Sale saved on this device"**, `Temporary receipt no. OFFLINE-<branch code>-<yyyymmdd>-<n>`, Total / Payment / Cash received / Change, a muted line **"It will be sent when you are back online."** (or "Log in again and it will be sent. Nothing was lost." after an expired login) and one button **New Sale**.
3. **New Sale** does **not reload** the page (a reload would show the offline page): it clears the cart, resets cash/payment, closes the dialog and focuses the search box. The cart is also removed from `sessionStorage` right when the sale is queued, so a reload can never bring a queued cart back.
4. **Non-cash** (GCash, Maya, Card, Bank): before saving, a notice "*GCash cannot be checked while you are offline…*" with a **Payment received** checkbox; **Save sale on this device** stays disabled until it is ticked. **Back** → the normal red "Not saved yet." card with Retry (nothing is queued). **Cash** is saved offline under the same rules as online (the cash-too-low check already ran before Confirm; the server repeats it).
5. **Queued sales hold their items on this device:** a queued device unit shows **"In a queued sale"** in the POS list (dashed amber card) and cannot be added; for accessories the queued quantity is subtracted ("57 in stock · 3 in a queued sale") and `+` stops there. Hint only — the server stays the truth.
6. **Hint** on POS, Sales Records, Dashboard, Inventory, Stock Monitoring, Stock Movement, Branch Transfers and Receive Stock: **"N queued sales are not counted yet."** (mixed with stock actions: "2 queued sales and 1 queued action are not counted yet."). Badge **Queued: N**, banner "Sending N queued items...", Outbox panel, Sign Out warning, "Please log in again…" pause: all the 6c-1 behaviour.
7. **Limits:** more than **50** queued sales, or the oldest queued sale older than **24 hours** → red line **"Please connect to the internet to send your sales."** in the hint and in the Outbox panel. Selling is never blocked.
8. **Outbox panel:** type **Sale**, summary `OFFLINE-… · 2 items · ₱1,500.00 · Cash`, "Sale made <time>", status Waiting / Sending... / **Sent ✓** / Needs action. After the server creates the sale the row shows **"Sale no. SALE-… (temporary receipt OFFLINE-… replaced)"** and stays 15 s (other items 4 s). Needs action: reason in plain English, **Review** (items, totals, device time; "No sale was recorded and no stock changed"; no "Open the form"), **Discard** ("Remove this sale from this device? It was not recorded. The owner will still see it in Needs Action.").
9. **Search while offline:** items returned by earlier searches on this device (branch staff only, `localStorage` `malbcoff_pos_seen_u<user>b<branch>`, newest 300) are used when the search request itself fails: "No internet. Showing N items seen earlier on this device. The server checks every item when the sale is sent." Without it a cashier could only finish the cart already on screen.

## Sending (reuses 6c-1 unchanged)
`actions/complete_sale.php` with headers `X-Outbox-Send: 1`, `X-Idempotency-Key`, `Accept: application/json`; one item at a time, oldest first; Web Locks per scope; backoff 5→15→60→120 s; network/5xx/`in_progress` = retry; 422/403/409 = **needs_action** (never retried, queue continues, reported to the owner); 401/419 = pause + resume after login; another user's items are never sent or shown. Payload = the checkout form fields (`branch_id`, `cart_json` with the typed `price_mode` + `price`, `payment_method`, `amount_received`, `payment_reference`) **plus** `offline_device_time` (ms, taken at the first tap of Confirm and kept across retries) and `offline_receipt_no`. **Never** `_csrf`, `client_key` or a token; the sender adds a fresh CSRF and the key at send time.

## Server rules (`actions/complete_sale.php`)
- **Everything is re-validated with the current session**: login, role, CSRF, branch = session branch (the posted `branch_id` is ignored), product, unit status `available` **at that branch** (`FOR UPDATE`), accessory stock, prices > 0 (Patch 8 rules), totals recalculated in cents from the line totals; browser `total`/`subtotal`/`unit_price` ignored. Completed sales are final (Patch 8 trigger).
- **Exactly once:** (1) `idempotency_keys` (6a, same transaction); (2) new hard guard `sales.client_id` **UNIQUE** — if the idempotency row was pruned (>30 days) the sale is still found by client id and returned as `replayed:true` ("already processed"); a client id that belongs to another user → 409; a unique-key race is caught and answered with the existing sale. `Idempotency::fingerprint()` now ignores `offline_device_time` / `offline_receipt_no`, so a first online attempt whose answer was lost and the later queued resend (which carries them) still match instead of 409.
- **Sale time:** only for a request with `X-Outbox-Send: 1`. The device time is accepted for `sales.created_at` (and for that sale's `sale_items.created_at` and `stock_movements.created_at`, so **Sales Records, Dashboard, Stock Monitoring and Stock Movement count the sale on the same day**) when it is **not in the future (+5 min) and not older than 7 days**; otherwise `created_at` = server time. `device_time` (as reported, if plausible: 2000…now+1 day) and `received_at` (server) are always stored. Online sales are untouched (server clock, no device time). Cross-day example tested: sale made 23:50 yesterday, sent today → counted yesterday everywhere.
- **Definite refusal = nothing saved** (the whole transaction rolls back; no partial sale, no idempotency row): unit already sold / transferred / in another branch / not found, not enough accessory stock (with counts), cash below total, price missing or 0, role changed. Messages name the item and identifier: `Samsung A15 (R5CT123) was already sold.`; the old "Please retry the sale." suffix is dropped for queued sends.
- Audit `sale.completed` carries `offline`, `device_time`, `receipt_no`.
- **Trust note:** a signed-in cashier could send a made-up device time within the 7-day window; the owner sees both times on the sale detail (Sales Records, owner only) and the audit log has them. Wrong phone clocks shift a sale by at most that difference; sales are never accepted in the future.

## Needs action (owner)
`actions/outbox_report.php` accepts `action_type: sale`; `details` can be 2000 characters (column widened by P3_005; 600 before it). The report holds the temporary receipt, **total, payment (and cash received / change or reference), device time, every item with identifier and amount**, plus the **reason**; branch and cashier come from the session. `/needs-action` shows type **Offline Sale**, "Cashier", "Sale made (device time)", the reason, the details; Dashboard card says "N saved items (sales or stock) need action". **Mark as resolved** + note records `resolved_by` / `resolved_at` / note (6c-1). No automatic "force sell"; resolution is manual (the owner talks to the branch and, if needed, re-rings the sale as a new normal sale).

## Sales Records
Offline sales show **Saved offline · OFFLINE-…** under the sale number; the sale detail shows "Saved offline — Receipt OFFLINE-…" and, for the **owner only**, "Made on device" and "Received by server". The date column is the device time (`created_at`). Old sales unchanged (columns NULL / 0; the page checks that the columns exist).

## Migration `database/migrations/P3_005_offline_sales.sql` (also appended to `deploy/migrations.sql`)
`sales.client_id CHAR(36) NULL` + **UNIQUE** `uq_sales_client_id`, `is_offline TINYINT(1) NOT NULL DEFAULT 0`, `device_time DATETIME NULL`, `received_at DATETIME NULL`, `offline_receipt_no VARCHAR(60) NULL`; `outbox_reports.details` → `VARCHAR(2000)`. Every step runs only when still missing (re-runnable, tested twice). Without the migration the app still works: sales save as before (and offline sends still use the idempotency key), only the client-id guard, the offline columns/marks and the long report are missing. Online sales now also store their `client_id`.

## Known limits (by design)
- A page cannot be **opened** while offline (6b offline page); only a page already open can queue and keep selling. Items not seen in an earlier search on this device cannot be found offline.
- The device clock decides the sale time within the rules above.
- A needs-action sale does not keep blocking its items on the device (only queued/sending ones do), so the cashier or owner can sell them again after sorting it out.
- Non-cash payments are only confirmed by the cashier ticking "Payment received"; the server cannot verify them either way.
- Browser data cleared / private window = queued sales on that device are gone (same as 6c-1); the Sign Out warning and the Queued badge are the guard.
- Owner, System Admin and impersonation have no outbox: their POS keeps the 6a Retry card.
